What C4 Is

C4, created by Simon Brown, is a lightweight model for describing software architecture at four levels of zoom: Context, Containers, Components, and Code.

The core idea is the map analogy. When you plan a trip you don't use one map; you zoom. A country map shows where a city sits, a city map shows its districts, a street map shows the route, and a floor plan shows the building. Each zoom level omits detail the audience at that level doesn't need. C4 applies the same discipline to software: instead of one sprawling diagram that tries to show everything and communicates nothing, you draw a small set of diagrams, each at one deliberate zoom level, each for a specific audience.

C4 is built on a simple set of abstractions rather than a heavyweight notation:

  • Person: a human user of our systems (an analyst, an operator, an administrator)
  • Software System: the highest level of abstraction; something that delivers value to its users, ours or someone else's
  • Container: a separately runnable or deployable unit that executes code or stores data (an application, an API service, a database, a message broker). Not a Docker container, though a container often ships in one.
  • Component: a grouping of related functionality inside a container, with a well-defined interface
  • Relationship: a labeled dependency between any of the above, always annotated with intent and technology

Why we're adopting it

  • Shared vocabulary across legacy orgs. We're converging teams with different diagramming habits. C4 gives every team the same words for the same things, which is a precondition for arguing productively about architecture.
  • Audience-appropriate communication. A Level 1 diagram works for the Director and mission partners. A Level 3 diagram works for the team writing the code. Nobody sits through a diagram that isn't for them.
  • Decisions become inspectable. When ADRs carry as-is and to-be diagrams at the right level, the architecture council reviews substance rather than prose.
  • Diagrams as code. C4 tooling lets us version diagrams next to the systems they describe, so drift is visible in a diff instead of discovered in an outage.

The Four Levels

Level 1System Context

The question it answers: How does this system fit into the world around it?

Shows the system as a single box, surrounded by the people who use it and the other systems it depends on or serves. No technology detail, no internals. This is the diagram you can put in front of anyone.

AudienceEveryone: leadership, mission partners, new team members, non-technical stakeholders
ElementsPeople, our system, external systems
Update rhythmWhen system boundaries or external dependencies change

Level 2Container

The question it answers: What are the major running pieces, what does each do, and how do they talk?

Zooms into the system to show its deployable units: web apps, API services, batch processors, databases, message brokers, file stores. Every container is labeled with its technology. This is the primary diagram for most architectural decisions and the workhorse level for our convergence work.

AudienceEngineers, architects, operations, security
ElementsContainers, data stores, people, external systems
Update rhythmWhen containers are added, removed, merged, or their protocols change

Level 3Component

The question it answers: What are the building blocks inside a container, and what is each responsible for?

Zooms into a single container to show its major components: the modules, services-within-the-service, and their responsibilities and interactions. Draw these where they earn their keep, typically for the containers where the complexity or the risk lives. Not every container needs one.

AudienceThe team that owns the container, reviewers of its design
ElementsComponents within one container, plus their external touchpoints
Update rhythmWhen the container's internal structure meaningfully changes; generation-assisted (see Automation and Generation)

Level 4Code

The question it answers: How is a component actually implemented?

Class diagrams, entity relationships, and similar. We do not hand-draw or hand-maintain Level 4 diagrams. If code-level diagrams are needed, generate them from the source with tooling on demand. Hand-maintained code diagrams are stale the day after they're drawn.

AudienceDevelopers working in the component
ElementsClasses, interfaces, tables
Update rhythmGenerated on demand, never maintained by hand

Notation Rules

C4 is notation-light, but not notation-free. These rules are what make one team's diagram readable by every other team.

  1. Every diagram has a title and a level. Format: [System Name] · System Context or [Container Name] · Components. Untitled diagrams don't get reviewed.
  2. Every element carries four things: name, type, technology (where applicable), and a one-line description of its responsibility. A box with only a name is a guess, not a diagram.
  3. Every relationship is a labeled arrow. The label states intent ("Submits collection requests to") and technology where it matters ("JSON/HTTPS", "NATS"). Unlabeled lines are ambiguity drawn with confidence.
  4. One level per diagram. Never mix zoom levels. If you need to show a container and its components, that's two diagrams.
  5. Every diagram has a key. Shapes and colors mean nothing on their own; the legend says what they mean on this diagram.
  6. Consistent element styling. People, our systems, containers, and data stores each get a consistent visual treatment; external systems are always hollow (white fill, solid outline) so they can never be confused with anything we own or change. Canonical diagrams color by level; ADR as-is/to-be diagrams color by change state (see the change palette in the ADR section).
  7. Diagrams live as code. Mermaid source files are committed to the repository alongside the system or the ADR that owns them. Exported images are artifacts of the source, never the source itself.
  8. Levels move together. Because each level is a separate file, a change that alters more than one level updates every affected diagram in the same commit. Levels that contradict each other are worse than no diagrams at all.

Deployment diagram rules

  • Icons supplement labels, never replace them. Every service still carries its name, technology, and detail in the bracket label. The diagram must survive grayscale printing and a reader who doesn't know the icon.
  • Commit the rendered SVG alongside the source. architecture-beta with custom icon packs does not render in stock repository markdown previews, so the rendering pipeline exports an SVG that gets committed next to the .mmd source. The source remains authoritative.
  • Icon pack is standardized: the org-hosted AWS Architecture Icons pack, registered under the aws: prefix at [INTERNAL HOST/PATH]. Browse available icon names at [INTERNAL CATALOG LINK]. No ad hoc icon packs.
  • Non-AWS elements use Mermaid's built-in icons (cloud, database, disk, server, internet) rather than mismatched vendor art.
  • All other notation rules still apply: title with environment, one environment per diagram, key included, change palette via the [NEW] / [CHANGED] / [REMOVED] tags in labels for ADR to-be versions.

Pre-review checklist

Run this before any diagram goes to a design review or the architecture council:

  • ☐ Title states the system and the level
  • ☐ Every element has name, type, technology (where applicable), and a one-line responsibility
  • ☐ Every relationship is labeled with intent, and technology where it matters
  • ☐ Exactly one zoom level on the diagram
  • ☐ Key/legend present
  • ☐ External systems visually distinct from ours
  • ☐ Mermaid source committed; image is an export, not the source
  • ☐ Fits its audience: could the intended reader understand it without you narrating?

Use in ADRs

An architectural decision without a diagram is a claim. The diagram is the evidence. Every ADR that changes structure carries C4 diagrams at the level of the decision.

Match the diagram level to the decision type

Decision typeRequired diagram levelExamples
System boundary, new external dependency, mission interfaceLevel 1Context (and System Landscape for portfolio-wide moves)Integrating a new external data provider; splitting or merging systems during convergence
Platform or technology selection, service topology, data store choice, protocol changeLevel 2ContainerReplacing a message broker; consolidating duplicated services into a shared platform capability
Internal design of a high-risk or high-complexity containerLevel 3ComponentRestructuring an access-control layer; introducing a new processing pipeline inside a service
Deployment, hosting, accreditation boundaryDeployment diagramMoving a workload between enclaves; environment topology changes
Critical workflow or failure behaviorDynamic diagramDocumenting the degraded-mode path a decision introduces

Rule of thumb: most ADRs need exactly one level, usually Container. If you can't name which level your decision lives at, you haven't isolated the decision yet.

Where diagrams go in our MADR template

  • Context and Problem Statement: the as-is diagram. Show the current structure the decision responds to. If no diagram of the current state exists, drawing it is the first step of the ADR, and it gets committed regardless of which option wins.
  • Considered Options: diagrams optional. Sketch an option only when the structural difference between options is the point of comparison; otherwise prose keeps this section light.
  • Decision Outcome: the to-be diagram. Same system, same level, same layout conventions as the as-is, so the diff is visible at a glance. This diagram becomes the authoritative picture of the target once the ADR is accepted.
  • Consequences: reference the delta in words: which containers appear, disappear, or change technology, and which relationships change. Durable rationale means a reader in three years can reconstruct why the shape changed.

The change palette

In ADR to-be diagrams, color encodes change state, not level (the title carries the level). This makes the decision's footprint readable at a glance: gray is the world you're not touching, blue is what the decision creates or changes, red is what it removes.

StateTreatmentTag
UnchangedGray fillnone
NewBlue fill[NEW]
ChangedBlue fill[CHANGED] plus a one-line note of what changed (technology, protocol, responsibility)
RemovedPale red fill, dashed red border, name struck through[REMOVED]
External systemHollow (white fill, solid outline), never gray[External]
  • The v1 rule: in the first ADR for a system, everything is blue with [NEW]. From then on, every subsequent ADR shows gray except its own footprint.
  • Tags are mandatory, color is reinforcement. Diagrams get printed in grayscale and read by colorblind reviewers; the [NEW] / [CHANGED] / [REMOVED] tags carry the meaning on their own.
  • Removals appear, then disappear. A removed element is shown in the to-be diagram in removal treatment so the decision to remove it is explicit and reviewable. Once the ADR is accepted and merged, it's deleted from the canonical diagram set entirely.
  • Changed relationships follow the same scheme: new or modified arrows in blue with their label noting the change; removed arrows dashed red.
  • As-is diagrams stay neutral: all internal elements gray, externals hollow. The as-is has no changes by definition; the palette does its work on the to-be.

Mechanics

  1. As-is / to-be pairs are mandatory for any ADR that changes structure. A to-be without an as-is hides the cost of the change.
  2. Diagram source lives with the ADR. Commit the Mermaid source in the ADR's directory. Rendered images are generated, never hand-edited.
  3. Accepted means canonical. When the council accepts the ADR, the to-be diagram is merged into the system's canonical diagram set. The canonical model always reflects accepted decisions plus reality, and drift between the two is a defect.
  4. Superseding updates the picture. An ADR that supersedes another must update the canonical model in the same change. No orphaned diagrams.
  5. Convergence ADRs use the System Landscape. Disposition decisions (invest, sustain, converge, sunset) show the landscape before and after, so the portfolio-level effect of each convergence call is visible to the council and traceable to the future state reference architecture.
05

Governance

  • Ownership: the architecture council owns this standard and the canonical models. Each system's owning team maintains its canonical diagram set; the council maintains the System Landscape and the future state reference architecture.
  • Design reviews check the diagram first. A review of structural work begins with the relevant C4 diagram at the right level. No diagram, no review.
  • Drift control: the canonical model is checked against reality at [CADENCE, e.g., each quarterly future state review]. Divergence is either fixed in the system or ratified in an ADR; silent divergence is not an option.
  • Tooling: [APPROVED TOOLS AND LOCATIONS, e.g., Mermaid sources at REPO PATH per system; ADR-embedded diagrams inline; rendering pipeline details]
  • Onboarding: every new engineer reads this standard and their portfolio's Level 1 and Level 2 diagrams in week one. If those two diagrams can't get a new engineer oriented, the diagrams need work.
  • Exceptions to this standard require an ADR. Naturally.

Automation and generation

The upper levels are decision records; the lower levels and supplementary diagrams are descriptions of what already exists. Decision records are authored by humans. Descriptions get generated, and no engineer should be hand-drawing what tooling can derive.

The policy in one sentence: generated drafts in, human-ratified canon out. Levels 1 and 2 are owned by staff engineers through ADRs and are never auto-regenerated, because a generator that redraws them from code would quietly launder undecided changes into official architecture. The annotation and scanning stack

Both stacks route through the same backbone: annotations in code produce a Structurizr model, and structurizr-cli exports that model to Mermaid (export -format mermaid), so the committed output still conforms to this standard's Mermaid-only rule. The Structurizr model is an intermediate build artifact, never the committed source of the canon.

  • Wrap both in internal packages ([e.g., @org/c4-annotations for npm, org-c4-annotations for Maven], published through [INTERNAL REGISTRY]) so teams take one dependency, the decorator vocabulary stays identical across languages, and we can swap the underlying implementation without touching every codebase.
  • The pipeline, end to end: annotations in code → scanner runs in the build → Structurizr model → structurizr-cli export -format mermaid → conforming C4Component Mermaid → CI diffs against the committed diagram. One command, no drawing.
  • Descriptions still come from humans: scanners discover structure, not intent. The one-line responsibility on each component (required by notation rule 2) lives in the annotation's description argument, so writing it is a code review concern rather than a diagramming chore.

How we make this real

  • An internal generation skill: we maintain a shared AI-assisted tooling setup ([e.g., a Claude Code skill / internal CLI]) that encodes this standard's Mermaid templates, notation rules, and change palette, so generated drafts come out already conforming. Located at [REPO/PATH]. Scanning a legacy codebase for the convergence inventory uses the same tooling.
  • Generated diagrams are labeled: title carries generation date and source path (same rule as Level 4), so shelf life is explicit and regeneration is a command, not a chore.
  • Drift detection in CI: for systems with generation wired up, CI regenerates Level 3 and Deployment diagrams and diffs them against the committed versions. A mismatch flags the owning team and the council. This automates the "drift is a defect" rule instead of waiting for quarterly review to catch it.
  • Review is the human contribution, not redrawing. A generated draft that's 90% right and corrected in review is the target workflow. If teams find themselves routinely discarding generated drafts, that's a signal the generation tooling needs fixing, and it comes to the council.
  • Levels 1 and 2 can use generated input, never generated output: scanners and LLM drafts are welcome as evidence when authoring or updating an ADR, but the canonical Context and Container diagrams change only through the ADR process.
